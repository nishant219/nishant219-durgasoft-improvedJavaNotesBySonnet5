## What this lecture covers

Multi-threading Part 4: **thread priority** as a third thread property,
alongside name (Part 3) and the thread life cycle (Parts 2–3). Sir covers the
valid range, the three named constants, why a scheduler cares about
priority at all, the `get`/`setPriority` methods, how default priority is
assigned to a brand-new thread, and — via two live demos — what actually
happens to execution order when priorities differ, including a platform
caveat when it doesn't.

## 00:08 — Every thread has a priority

Priority is a thread property, just like name: every thread gets either a
**default priority generated by the JVM**, or a **custom priority set by the
programmer**.

### 01:11 — Valid range: 1 to 10, not 0 to 10

The recurring point of confusion: is the range 0–10 or 1–10? Priority is
**not an array index**. The valid range of thread priorities is **1 to 10**
— 0 is not a legal priority.

### 02:16 — Which end is min, which is max (the rank story)

Sir's analogy: two parents at his village library, comparing their kids'
entrance-exam ranks. One kid scored rank 2,500 and the parent calls it
"worst"; the other scored rank 148,000 and the parent calls it "best." Both
parents are illiterate about how ranks work — a **small** rank number is
actually the **good** one. The moral: don't assume a number's meaning from
its size, and don't map that intuition onto priorities either.

Thread priority is the opposite of exam rank: **the bigger the number, the
higher the priority.**

- **1 = minimum priority**
- **10 = maximum priority**

### 07:15 — The three priority constants

`Thread` defines three constants for the standard priority values:

```java
Thread.MIN_PRIORITY   // 1
Thread.NORM_PRIORITY  // 5
Thread.MAX_PRIORITY   // 10
```

**Board:**

> - Every thread in Java has some priority — default priority generated by
>   the JVM, or customized priority provided by the programmer.
> - Valid range of thread priorities is **1 to 10**, where **1 is min
>   priority** and **10 is max priority**.
> - `Thread` class defines the following constants to represent some
>   standard priorities: `MIN_PRIORITY` (1), `NORM_PRIORITY` (5),
>   `MAX_PRIORITY` (10).

## 13:15 — Why priorities exist: the traffic-signal analogy

A four-way traffic signal, all lanes carrying ordinary traffic, cycles
clockwise or anticlockwise by some fixed algorithm. Now a minister's
convoy approaches from one side — the police stop the cycle and let the
minister go first, because a minister outranks ordinary traffic. Escalate
the story: a Chief Minister outranks a minister, a Prime Minister outranks
a CM, the President outranks a PM. Whoever holds the **highest priority**
goes first when several parties are competing for the same resource.

Substitute "the processor" for "the junction" and "threads" for "vehicles":
when multiple threads are waiting for their turn, the **thread scheduler**
uses priority to decide who goes first. Sir's numeric example: threads with
priorities 8, 7, 6, 4 get the processor in that same order — highest first.

If two threads share the **same** priority (his example: two threads both
at 7), there is **no guaranteed order** between them — it depends on how the
underlying thread scheduler behaves (round robin, FCFS, or something else).

**Board:**

> - Thread scheduler will use priorities while allocating the processor.
> - The thread which has the highest priority will get the chance first.
> - If two threads have the same priority, we can't expect an exact
>   execution order — it depends on the thread scheduler.

## 20:59 — `getPriority()` / `setPriority()`

Same shape as `getName()`/`setName()` from the previous video:

```java
public final int getPriority()
public final void setPriority(int newPriority)
```

**Allowed values: 1 to 10.** Anything else throws `IllegalArgumentException`
at runtime — it compiles fine, but fails the moment it runs:

```java
Thread t = new Thread();
t.setPriority(7);    // valid
t.setPriority(17);   // compiles; throws java.lang.IllegalArgumentException at runtime
```

Verified: `setPriority(15)` and `setPriority(17)` both compile and both
throw `IllegalArgumentException` when executed — confirmed on JDK 26.

> ⚠️ **Modern Java — priority is nearly inert on a virtual thread (Java 21).**
> Everything above is unchanged for a regular ("platform") thread. But a
> **virtual thread** (Project Loom, JEP 444, Java 21) always reports
> `Thread.NORM_PRIORITY` (5), and calling `setPriority(...)` on one is a
> silent no-op — the value is simply discarded:
>
> ```java
> Thread vt = Thread.ofVirtual().unstarted(() -> {});
> vt.setPriority(10);
> System.out.println(vt.getPriority());   // 5 — the setPriority call did nothing
> ```
>
> Verified on JDK 26. The range check still runs first and still throws
> `IllegalArgumentException` for an out-of-range value on *any* thread,
> virtual or platform — only the "actually change something" half is
> skipped for virtual threads. This makes sense once you know why virtual
> threads exist: there can be millions of them multiplexed onto a handful of
> real OS threads, so giving each one its own OS scheduling priority isn't
> meaningful.

## 26:49 — Default priority: main vs everyone else (a trap question)

Sir poses it as a trap: is the default priority **5 for every thread**, or
**5 only for the main thread**? The more specific answer is the correct one:

- **Default priority for the main thread is 5.**
- **For every other thread, the default priority is inherited from its
  parent thread** — whatever priority the parent has at the moment of
  creation, the child gets the same value. Parent 10 → child 10. Parent 7 →
  child 7.

### 31:15 — Demo: priority inheritance, and parent *thread* vs parent *class*

```java
class MyThread extends Thread {
}

class Test {
    public static void main(String[] args) {
        System.out.println(Thread.currentThread().getPriority());
        // 5 — the JVM's default for main

        // Thread.currentThread().setPriority(15);
        // compiles; throws IllegalArgumentException at runtime — 15 is out of range

        Thread.currentThread().setPriority(7);   // line one
        // main thread's priority is now 7

        MyThread t = new MyThread();   // this line is executed BY main
        System.out.println(t.getPriority());
        // 7 — inherited from main, NOT a fixed 5
    }
}
```

Verified on JDK 26: prints `5` then `7`, exactly as taught.

If line one is commented out, main stays at its default of 5, so `t`
inherits **5** instead — the practical proof that the child copies whatever
its parent's priority happens to be at creation time, not a hard-coded
default.

**Critical distinction Sir draws:** `MyThread`'s **parent class** is
`Thread` (`extends Thread`) — that never changes. `t`'s **parent thread** is
whichever thread executed `new MyThread()` — here, `main`. The two words
"parent" answer completely different questions, and mixing them up is the
usual source of confusion on this topic.

## 43:24 — Demo: different priorities changing execution order

```java
class MyThread extends Thread {
    public void run() {
        for (int i = 0; i < 10; i++) {
            System.out.println("Child Thread");
        }
    }
}

class ThreadPriorityDemo {
    public static void main(String[] args) {
        MyThread t = new MyThread();
        t.setPriority(10);   // line one
        t.start();
        for (int i = 0; i < 10; i++) {
            System.out.println("Main Thread");
        }
    }
}
```

**If line one is commented out:** both threads default to priority 5, so
there is no guaranteed order — either interleaving, or either thread
finishing first, is possible.

**If line one stays in:** main is priority 5, the child is priority 10, so
the higher-priority child is *expected* to get the processor first:

```text
Child Thread   (×10)
Main Thread    (×10)
```

### 52:27 — Platform twist: priority support is not guaranteed everywhere

Running this same program live, Sir gets the expected `Child Thread ×10`
then `Main Thread ×10` sometimes, but on his demo machine (**Windows 7**) he
also sees mixed or reversed output (`Main`, `Child`, `Main`, ...) even with
`setPriority(10)` still in the code and the file properly saved. His
conclusion, stated on the board:

> Some platforms won't provide proper support for thread priorities.

Priority is a hint to the underlying OS scheduler, not a guarantee from the
JVM — some operating systems (his example: Windows 7) don't honor it
reliably. If your own output doesn't match what's "expected" here, the
program isn't necessarily wrong; the underlying platform's scheduler may
simply not be respecting priority the way you'd hope. This has always been
true and remains true: the JLS documents priority as advisory, and the
degree to which any given OS actually reorders threads by priority is an
implementation detail outside the JVM's control.

## Exam and interview points

1. **Valid priority range is 1 to 10, not 0 to 10** — priority is not an
   array index, and 0 is invalid.
2. **1 is `MIN_PRIORITY`, 10 is `MAX_PRIORITY`, 5 is `NORM_PRIORITY`** —
   bigger number means higher priority, the opposite of a competitive-exam
   rank.
3. **No `LOW_PRIORITY` or `HIGH_PRIORITY` constants exist.** Only `MIN`,
   `NORM`, and `MAX` — a favorite planted trap.
4. **`getPriority()`/`setPriority(int)` are both `public final`.**
   `setPriority` accepts only 1–10; anything else compiles but throws
   `IllegalArgumentException` at runtime.
5. **Default priority is 5 only for the main thread.** Every other thread
   inherits its priority from whichever thread created it, at the moment of
   creation — not a fixed value.
6. **"Parent class" and "parent thread" are unrelated ideas.** A class's
   parent is fixed by `extends`; a thread's parent is whichever thread
   executed the `new` that created it. `MyThread extends Thread` but is
   parented, as a thread, by whoever ran `new MyThread()`.
7. **The thread scheduler prefers the highest-priority runnable thread**,
   but gives no guaranteed order between threads of equal priority.
8. **Priority is an advisory hint to the OS scheduler, never a guarantee**
   from the JVM — some platforms honor it more reliably than others. Don't
   build correctness-critical logic on priority ordering.
9. **On a virtual thread (Java 21), priority is effectively frozen at
   `NORM_PRIORITY` (5)** — `setPriority(...)` is a documented no-op, since
   there is no single OS thread to prioritize underneath it. The 1–10 range
   check and its `IllegalArgumentException` still apply to every thread,
   virtual or platform.
